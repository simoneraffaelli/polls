# Registrazione e calcolo del modello

Il modello non parte automaticamente e non dispone di prior, domande previsionali o orientamenti politici 2026 precompilati. I provider attuali non dimostrano la copertura delle singole gare. I comandi sotto servono a registrare dati verificati in un ambiente controllato; non sostituiscono la verifica di provenienza, calendario e significato delle opzioni.

Eseguire prima le migrazioni, l'installazione delle code e `pnpm worker:build`. Usare le variabili PostgreSQL del runtime. I file JSON di input vanno tenuti fuori dal repository e limitati all'operatore; i comandi non accettano contenuti o password come argomenti della riga di comando. Per le registrazioni è necessario un utente con appartenenza amministrativa attiva. Gli ID restituiti dai comandi servono per i passi successivi.

1. Registrare una domanda con `MODEL_QUESTION_FILE` e `pnpm model:register-question`. Il JSON contiene `scope` (`sectionId`, `editionId`), `raceId` UUID oppure `null`, `slug`, `outcomeDefinition` (`seat_majority` o `chamber_control`), `resolutionRuleVersion`, `actorUserId`, `reason` e `cutoff` con `version: 1`, `localDateTime` (secondi, senza offset), `timeZone` IANA, `utcInstant` e `calendarReference` HTTPS. Ora locale e istante UTC devono concordare. La registrazione crea anche la prima revisione del termine e l'audit nella stessa transazione. Una domanda registrata dopo il termine nasce chiusa.
2. Registrare la struttura con `STRUCTURAL_REFERENCE_FILE`, `REVIEWER_USER_ID` e `pnpm model:register-structure`. Il JSON contiene `questionId`, `scope`, `version`, `sourceUrl` HTTPS, `sourceVersion`, `availableAt` e `payload` conforme a `structuralReferencePayloadSchema`. Ogni gara deve appartenere all'edizione; prior, regole di risoluzione e controllo della camera devono avere provenienza e disponibilità reali. Versione e contenuto sono immutabili. La data dichiarata di disponibilità da sola non anticipa l'acquisizione effettiva.
3. Dopo avere importato un sondaggio e ottenuto gli ID di revisione e collegamento, registrare l'orientamento delle opzioni con `POLL_OPTION_MAPPING_FILE`, `REVIEWER_USER_ID` e `pnpm model:register-mapping`. Il JSON contiene `structuralReferenceId`, `revisionId`, `externalQuestionId`, `raceId`, `positiveOptionId`, `negativeOptionId` e `reason`. Le opzioni sono ID esatti della revisione, non etichette interpretate automaticamente. Una rettifica crea una nuova mappatura; i run già pubblicati conservano il vecchio riferimento.
4. Preparare un file di richiesta per l'assemblatore con `questionId`, `scope`, `structuralReferenceId`, `inputAsOf` UTC, `kind`, `modelVersion`, `parameters` completi e `seed`. Impostare `MODEL_ASSEMBLY_FILE` e `MODEL_ITERATIONS` (100–20.000), poi eseguire `pnpm model:enqueue-reviewed`. L'assemblatore legge dal database la struttura registrata e le ultime revisioni sigillate dei sondaggi, con collegamenti e orientamenti delle opzioni idonei. Ricava il margine dalle percentuali originali. Rifiuta domande chiuse, struttura incompleta, input futuri, fonti escluse, correzioni incompatibili, assenza di sondaggi e più di 500 segnali. Una revisione con più domande mappate non è scelta arbitrariamente: la richiesta si arresta e richiede una selezione esplicita futura. Le decisioni amministrative più recenti valgono per un nuovo run, anche quando `inputAsOf` è precedente alla decisione. La policy iniziale assegna qualità 1 ai sondaggi acquisiti senza fingere un rating empirico.
5. `MODEL_SNAPSHOT_FILE` con `pnpm model:enqueue` resta disponibile per snapshot completi preparati da strumenti locali controllati; `pnpm model:run` esegue lo stesso calcolo direttamente senza coda. Il bridge verifica in ogni caso riferimenti, valori raw, struttura, scadenza e pubblicazione. Ogni richiesta limita il file a 5 MB e il prodotto iterazioni × gare a 5 milioni. La coda ritenta gli errori transitori; la chiave immutabile domanda + hash snapshot + iterazioni evita nuovi run dopo un retry confermato. La simulazione avviene nel worker, mai durante una visita web. Non è configurato alcun ciclo automatico di pronostici.

Solo un risultato completo di tipo `forecast`, con input verificati e registrati entro `inputAsOf`, può essere pubblicato. Scrittura e termine usano il tempo del database. Una ricostruzione retrospettiva resta separata e non pubblica una nuova previsione. La lettura pubblica restituisce soltanto un run sigillato realmente pubblicato, marcato come corrente oppure congelato secondo il tempo del database. Lo stato rimane **sperimentale** finché la validazione prevista dal piano non è conclusa.
